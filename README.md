# Задание 1. Анализ и планирование
### 1. Описание функциональности монолитного приложения
1.1 Пользователи-клиенты могут получить информацию о датчиках в своем доме (вместе с данными о температуре) через веб-интерфейс

1.2 Пользователи-клиенты могут получить информацию о конкретном датчике (вместе с данными о температуре) через веб-интерфейс

1.3 Пользователи-клиенты могут устанавливать нужное значение температуры на конкретном датчике через веб-интерфейс

1.4 Пользователи-клиенты могут управлять статусом конкретного датчика через веб-интерфейс

1.5 Специалисты могут подключить новый датчик к системе

1.6 Специалисты могут изменять настройки существующего датчика (включая темперутуру и статус)

1.7 Специалисты могут удалять датчик из системы

### 2. Анализ архитектуры монолитного приложения

Язык программирования: Go

База данных: PostgreSQL

Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.

Взаимодействие: Синхронное, REST API. Взаимодействие с датчиками = Push.

Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.

Развертывание: Требует остановки всего приложения.

### **4. Проблемы монолитного решения**
Проблемы текущего решения связаны не только с монолитностью, но и с нынешней заложенной функциональностью

Несоответствие текущей реализации бизнес-целям:
- пользователь-клиент не может самостоятельно подключить / настроить / отключить устройство;
- система не поддерживает устройства, кроме датчиков температуры, в частности: свет, ворота, систему наблюдения;
- система не поддерживает сложные сценарии работы;
- система не предполагает интерфейс работы команды поддержки.

Сложности масштабирования:
- PUSH-коммуникация со стороны сервера может привести к неоптимальной загрузке, если число подключенных устройств будет значительно расти;
- монолитная архитектура повышает time-to-market доработок;
- монолитная архитектура усложняет поддержку реализации.

# Задание 4. Создание и документирование API

### 1. Тип API

Для взаимодействия используется REST API, кроме некоторых случаев, где применяется асинхронное взаимодействие через MQ-брокера:
